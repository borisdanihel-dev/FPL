## 3. The workflow — `.github/workflows/nightly.yml`

- `cron: "40 21 * * *"` + `workflow_dispatch`. 21:40 UTC is 23:40 Prague until clocks change on 25 Oct, 22:40 after.
- `ubuntu-latest`, `setup-python` 3.14 (your local version), `pip install -r requirements.txt` (created: comments only, standard library; pip exits 0 on it), then `python fpl_nightly.py`.
- `fpl_nightly.py` runs the batch file's steps in the same order — tests → sync → record ×4 → report — with no Windows paths and no Drive ship. The dated export goes to `exports/`, the run log to `logs/`.
- Requests: browser-style User-Agent, three retries with doubling backoff (2, 4, 8 s). A request that never succeeds makes the sync exit non-zero after saving what it fetched.
- Commit-back runs with `if: always()`: `projection_log.csv`, `fpl.sqlite`, `exports/`, `logs/`, `reports/` as `nightly <date> [skip ci]`. Any failure exits 1, the run goes red, GitHub mails you; the log is committed even then.

## 4. `fpl.sqlite`

1.32 MB (1,323,008 bytes; 0.43 MB gzipped). Under 20 MB, so it is **committed**, and the runner commits it back each night. It holds the only copy of `price_history` (16,543 rows, about 662 and 29 KB a day), which the API cannot return, so a per-run rebuild would lose it and `actions/cache` is not durable (evicted after 7 unused days). Projected ~8 MB by GW38; git keeps one version per night, at worst ~350 MB of history over the season before GitHub's packing. `projection_log.csv` never depends on it: `fpl_edge.py` does not import sqlite and records from the export alone (tested with no database in the folder).

## Decisions I made that you may want to change

- **Any failure is red on the runner, including a failed sync** (the batch file treats a failed sync as non-fatal). A red sync night still re-records from the last good export, as the batch file does.
- **`exports/` is seeded** with the fourteen dated exports that exist (GW3, GW4, twelve GW5), and the existing `reports/*.txt` are committed, because `reports/` is now tracked and the runner will write files of the same names.
- **The batch file's own logs stay local** (`reports/run_*.log` ignored); the runner's go to `logs/`.

## One risk I noticed, not changed

`test_real_export_value_is_prices_plus_bank` reads the live export, and the suite gates the record on both paths. It fails if price drift since the deadline reaches £1.5m in total, or reaches the bank when the bank is £0.5m or more. With a bank just above £0.5m, an ordinary week's price changes could turn the gate red and block the forecasts. Your call whether a data check belongs in the gate.
