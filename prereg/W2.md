## Amendment 3: the multiplier check's chip lookup (Boris, 21 Oct, after dry/W2's check 31; verbatim below)

Pinned before the fix.

> W2 check 31: the data is complete. fpl.sqlite has entry 4866471's chip (chips: 3xc, event 7, 2026-10-17T09:48Z; entry_gw GW7 active_chip '3xc'; data 7dbc319 and data-dryrun-W2). So "chip None" is W2's lookup, not a missing record. Our own GW7 Triple Captain passes. Check whether the lookup keeps only one chip per entry (his rows are 3xc GW7, then wildcard GW6). Fix it on w2-wip with a test (an entry with chips in two consecutive gameweeks, in both row orders), the verifier on the diff, and a fresh dry/W2 run green before Saturday's merge.

**What the check found** (a copy of data `7dbc319`, read-only):
- The lookup does not keep one chip per entry. `entry_gw` holds both of
  4866471's chips (GW6 wildcard, GW7 3xc), one row per gameweek, and the
  lookup is per (entry, gameweek).
- The cause is elsewhere. `check_multipliers` reads the chip from
  `totals_chain`'s result.
  - The chain settles gameweek g only with the row of g + 1 (S9's
    correction of provisional rows).
  - GW7 is the newest settled gameweek and has no GW8 row yet, so the
    chain excludes it for every entry.
  - Yet GW7's picks are checked, so their chip reads as None.
- **Our own entry is in the same case:** a 3xc in GW7, Haaland ×3, also
  excluded from the chain. The check stopped at 4866471 first.
- The offline S9 tool (`tools/league.py`, of which `fpl_league.py` is the
  verbatim copy) carries the same lookup.

**The fix (pinned):**
- `load` passes the stored `entry_gw` rows (every gameweek as fetched,
  with `active_chip`) to `check_multipliers`, in place of the chain's
  settled scores. The multiplier rule depends on the chip played, which
  `entry_gw` records whatever the chain can settle.
- The same one-line change goes into `tools/league.py` and
  `fpl_league.py`, so the verbatim copy holds (the W2 copy test).
- Nothing else changes: the chain, the variance, the scores and the
  rule.

**Tests** (in `tests/test_W2.py`):
- an entry with chips in two consecutive gameweeks (wildcard GW6, 3xc
  GW7), its `entry_gw` rows inserted in both orders. GW7 is the newest
  settled gameweek, with no GW8 row. The 3xc multiplier passes, and a
  wrong multiplier still stops the run.
- Red on the old lookup. A mutation that keeps one chip per entry is red
  too.

**Then:** the full suite; the verifier on the diff; a fresh `dry/W2` run
green before Saturday's merge; report and CHANGELOG on `w2-wip`.
