# S5 — Step 5 (P3, odds-implied fixture λ: model and backtest, offline)

Committed before any code for this item. Lane B, offline work:
`tools/odds_lambda.py` is never imported by the nightly. The live Odds API
collector is lane A's W1 (ruling 1); nothing here touches `ODDS_API_KEY`.

- **Item:** S5 (BUILD_PLAN.md Step 5, item P3; the λ model, the fallback,
  the source `bottomup_lambda` and its backtest).
- **Hypothesis:** a Poisson λ per team-fixture implied by pre-closing match
  odds predicts clean sheets better than `bottomup`'s team-rate Poisson, and
  moves the DEF/GK forecast with the opponent as the flat fixture term does
  not.
- **Data and sample filter:**
  - *Odds (ruling 2):* football-data.co.uk Premier League CSVs (E0) for
    2025/26 and 2026/27 to date, downloaded only after Boris's approval in
    chat and stored under `tools/odds/E0_<season>_fetched_<YYYY-MM-DD>.csv`
    (committed, so the verifier reproduces the run; fetch date in the name).
    Columns used: pre-closing average odds `AvgH`, `AvgD`, `AvgA`,
    `Avg>2.5`, `Avg<2.5`; where a row lacks them, Bet365 `B365H/D/A`,
    `B365>2.5`, `B365<2.5`. Never a closing column (any name ending in `C`
    or containing `CH/CD/CA`), never Pinnacle (`PS*`, `P>2.5`, `P<2.5`).
    Rows join fixtures on (date, home team, away team) through a committed
    team-name map; an unmapped row stops the run. Known limitation, stated
    up front: football-data's pre-closing odds carry no fetch time; they are
    collected before kickoff (Friday / Tuesday afternoons), which is not
    proven to be before the FPL deadline (90 minutes before the first
    kickoff). The backtest records this; the live source (W1 snapshots)
    is timestamped and is what forecasts will use.
  - *Players and outcomes:* 2025/26 as S4 (`historical/2025-26/`, rounds
    < g only; realised points under 2025/26 rules); 2026/27 from the dated
    exports in `C:\GIT\FPL-data\exports` (the newest export dated on or
    before each deadline) and `player_gw` for actuals, settled gameweeks
    only (lockdown guard). Local data read-only; output under `--out`.
  - *Primary sample (as BUILD_PLAN Step 5 item 4):* 2025/26, GK and DEF
    with >= 60 minutes in the fixture, rolling origins GW5–38 (GW1–4 have no
    training window for `bottomup`'s team rates, so the pair is compared
    where both exist). The 60-minute condition is the clean-sheet
    eligibility rule applied to the outcome, the same realised set for both
    models; it is not a forecast filter.
  - *2026/27 condition:* GW4 to the latest settled gameweek (GW1–3 have no
    dated export); starters = forecast P(start) >= 0.8 from the same export;
    DEF and GK.
- **Comparison:** `bottomup_lambda` against `bottomup`, both rebuilt from the
  same pre-deadline inputs (`bottomup` rebuilt equals the recorded rows where
  the log has them — tested). Fallback share (fixtures without odds) printed
  per gameweek, with which source fired per fixture.
- **Primary metric (one):** Brier score of P(clean sheet) per gameweek on
  the primary sample; per-gameweek paired difference bottomup minus
  bottomup_lambda (positive = improvement).
- **Secondary metrics (information only):** log loss of P(clean sheet); the
  DEF realised-points spread between the easiest and hardest opponent
  quintiles by λ_opp (2025/26 starters; currently about 0.17 by FDR, expected
  >= 1.0); the 2025/26 starters DEF/GK Spearman of both sources; the
  proportional-margin variant's Brier (the model uses the power method).
- **Bootstrap:** unit = gameweek, 10,000 resamples, 90% CI (percentile),
  paired, seed 20261018 — the S4 harness.
- **Pass threshold:** (a) mean per-gameweek Brier improvement >= 0.005 with
  the 90% CI excluding 0 (lower bound > 0) on 2025/26; AND (b) 2026/27,
  starters-only DEF/GK Spearman does not fall: the 90% CI of the mean
  per-gameweek difference (bottomup_lambda minus bottomup) has its upper
  bound >= 0 — "no detectable fall" — printed with the S4 power
  calculator's G for Δ = 0.02 at the s_d measured on 2025/26 for this pair,
  so the reader sees how detectable a fall was. Adoption of
  `bottomup_lambda` as an input to any decision needs Boris's acceptance in
  chat (ruling 3); until then it is recorded under its own name only.
- **Acceptance tests (in addition):**
  1. De-margin: proportional (p_i = q_i / Σq) and power (p_i = q_i^k with k
     solved by bisection so Σp = 1); both sum to 1 within 1e-9 on hand
     cases; the power method is the forecast's.
  2. λ_total from P(under 2.5) by bisection on the Poisson CDF at 2 goals;
     home/away split by bisection on P(home win) under independent Poisson
     (the Skellam sum, computed exactly to 15 goals each); P(clean sheet for
     team) = exp(−λ_opponent). Hand case: symmetric odds give λ_h = λ_a.
  3. Fallback when a fixture has no odds row: a time-decayed Poisson team
     model — attack and defence strengths by iterative Poisson fit on
     results before the deadline, weights exp(−0.0065 × days before the
     deadline) (Dixon–Coles' ξ), league average for a team with fewer than
     4 weighted matches; the fixture's source ("odds" / "fallback") is
     printed. Mutation: fallback fed a future result → red.
  4. `bottomup_lambda` = `bottomup` with its clean-sheet term's λ replaced
     by the odds λ_opp (fallback when missing) and a goals-conceded term for
     GK/DEF, −P(start) × E[floor(GC/2)] under Poisson(λ_opp) (summed to 15
     goals). Unit test (Step 5 item 3): P(clean sheet) moves with opponent
     strength — a stronger opponent's odds give a lower P(cs), every other
     input equal.
  5. Point-in-time: for three gameweeks (earliest, middle, latest) the
     forecast is rebuilt from inputs dated before the deadline only and
     matches within 1e-9; a mutation reading the odds row of a later match
     → red.
  6. CLI: `python tools/odds_lambda.py --season 2025-26 --test`,
     `--season 2026-27 --condition`, `--fixture <home> <away>` (prints λ,
     source, P(cs)); nightly isolation test as S4; tests in
     `tests/test_S5.py`. No file the item adds contains a key, an `apiKey=`
     URL or an Authorization header (verifier check 7).

No re-tuning after viewing results.
